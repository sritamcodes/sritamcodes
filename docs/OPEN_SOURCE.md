## 🔧 3. Pull Request Guidelines

When submitting a pull request:

### Keep changes focused

A PR should ideally solve **one problem or add one feature**.

### Write clear commits

Prefer descriptive commit messages:

```text
feat: add search functionality
fix: resolve mobile layout issue
docs: improve installation guide
refactor: simplify data processing
```

### Test before submitting

Make sure the project still works after your changes.

### Explain your changes

A good PR should briefly explain:

- What changed?
- Why was it needed?
- How was it tested?
- Are there any limitations?

## 🐛 4. Reporting Issues

Found a bug?

Create an issue with as much useful information as possible.

```text
TITLE:
Short description of the problem

ENVIRONMENT:
OS / Browser / Python / Node / etc.

EXPECTED:
What should have happened?

ACTUAL:
What actually happened?

STEPS:
1. Step one
2. Step two
3. Step three

SCREENSHOT / LOG:
If applicable
```

Good bug reports make problems much easier to reproduce and fix.

---

## 💡 5. Feature Requests

Have an idea for improving a project?

Open an issue and explain:

- 💡 What feature you want
- 🎯 What problem it solves
- 👥 Who would benefit from it
- 🔧 How you think it could work
- 📌 Any examples or references

Not every feature will necessarily be implemented, but thoughtful suggestions are always useful.

## 📚 6. Documentation Contributions

Documentation is an important part of open source.

Contributions can include:

- Fixing spelling or grammar
- Improving installation instructions
- Adding examples
- Clarifying confusing sections
- Updating outdated information
- Adding project explanations

Even a small documentation improvement is a valid contribution.

## 📜 8. Licensing

Each repository may have its own licensing terms.

**Always check the `LICENSE` file of the specific repository before using, modifying, or redistributing its code.**

If a repository does not contain a license, do not assume that its code is freely reusable.
